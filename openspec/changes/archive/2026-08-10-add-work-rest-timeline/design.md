## Context

应用当前由 `domain.Monitor` 管理 `waiting`、`working`、`idle-paused` 和 `resting` 状态，`App.Status()` 与后台输入/定时器负责推进状态，前端每秒读取状态并更新主界面。当前没有状态转换历史，因此用户只能看到当下状态。

本变更只需要覆盖当前应用运行周期，桌面工具退出或重启后不要求恢复历史。记录不得包含键盘内容、鼠标坐标或窗口信息。

## Goals / Non-Goals

**Goals:**

- 在状态实际发生转换时记录区间的开始和结束时间。
- 通过一个简单的 Wails 方法向前端提供按开始时间排序的记录。
- 前端展示工作段、休息/暂停区间、持续时间和当前进行中的区间。
- 保持现有 `Monitor` 的计时和提醒规则不变。

**Non-Goals:**

- 不做磁盘持久化、历史日期查询、导出或统计分析。
- 不记录原始输入事件及其来源细节。
- 不重建前端状态机，不改变现有设置和通知行为。

## Decisions

- **由 App 持有时间线。** `Monitor` 继续只负责状态转换和计时，`App` 在调用 `Advance`、`EffectiveActivity`、`PauseForIdle` 前后比较状态并维护区间。这样不把 UI/历史展示需求耦合进领域计时规则；相比让前端根据轮询结果推断转换，后端能捕获一秒轮询之间发生的边界。
- **仅内存保存当前会话。** 使用 `[]TimelineEntry` 和一个当前开放区间，应用创建时为空，关闭或重启自然清空。相比增加文件格式和迁移，满足“简单记录”且避免隐私与持久化复杂度。
- **以状态作为记录类型。** 记录使用 `working`、`resting`、`idle-paused` 三种类型；`waiting` 不产生记录。每条记录包含开始时间、可选结束时间和持续秒数，当前记录的结束时间为空并由查询时按当前时间计算。
- **新增只读 `Timeline()` API。** 该 API 返回复制后的记录快照，前端独立渲染垂直列表；相比扩展 `Status` 为嵌套历史，保持现有状态契约简单，并允许时间线单独刷新。
- **前端沿用现有轮询。** 每秒调用时间线查询并刷新当前条目，复用已有的 Wails 轮询节奏；不新增事件总线或状态管理库。

## Risks / Trade-offs

- [应用运行时间很长时内存列表持续增长] → 仅保留当前日期的记录，跨日期时清空；在本变更范围内不做持久化和无限历史。
- [状态转换发生在两次前端刷新之间] → 后端在每个状态推进入口统一记录转换，不能依赖前端轮询推断。
- [后台时钟或测试时间非单调] → 忽略早于当前区间开始时间的结束时间，避免产生负持续时长。

## Migration Plan

无需迁移。新增 API 和前端区域随应用版本发布；回滚时删除时间线 API 和 UI 即可，不影响已有设置文件。

## Open Questions

无。当前版本明确只展示本次运行期间的记录，不提供历史恢复。
